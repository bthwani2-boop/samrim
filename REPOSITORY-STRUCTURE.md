## Placement and simplification law
1. Put authored logic with the owner of **its changing responsibility**, not a historical screen, team, refoundation batch name or convenience folder.
2. Business records and mutations belong to their service owners; apps compose views and invoke contracts, they never become a second business writer.
3. Each exposed API and generated client has a recorded original source; derived files must be reproducible and are never hand-maintained as independent truth.
4. One Store ID and one DSH commerce engine serve Store relation variants. An owner-person and an owned Store must never be collapsed into one entity or identity.
5. Prefer explicit stable domain names. Avoid `shared`, `common`, `misc`, `legacy`, `new`, `v2`, dates in **live code names**, and old workflow vocabulary without justified semantics.
6. Before removing or relocating a file, trace all direct/dynamic consumers, database schema references, environment keys, routes, tests and external identity/URL contracts. Transfer unique behavior, change consumers, prove it, then remove the losing implementation.
7. No number-of-files target, mandatory 'clean' architecture folder ladder, or second configuration/permission/financial policy writer.
8. Preserve externally issued Expo app package/bundle IDs, EAS project identity, deep links, signing identities and historical financial/legal records until an independently approved migration proves safety.
9. A new general tool/package requires at least one established cross-owner consumer and a reason owner-local code is inadequate.
10. Reference/benchmark URLs retain original evidence status, publication date and usage caveats; never become copied product rules.

## Progressive application and screen-migration boundaries

- The existing top-level `apps/<surface>/app/` is the **only active route root** for Expo Router or Next App Router. Do not create a competing `src/app/`; a future route-root move is a single reviewed refactor with route/deep-link checks.
- `apps/customer`, `apps/merchant`, `apps/captain` are Expo **presentation hosts**; `apps/control-panel` is the Ant Design/Next **Operator** host. Internal folder names do not rename externally issued app slugs, Android/iOS IDs, EAS projects or public URL/deep-link contracts. Historical `app-partner` is the preserved Merchant mobile identity, not a fifth application.
- `src/features/<capability>/` is an allowed **private presentation unit**, not a business engine, API authority or permission to copy donor folders. No `features`, `bootstrap`, `shell` or `tests` directory is mandatory while empty; create one only when an approved consumer and test need it. Next may colocate small route-specific UI under its existing App Router conventions; avoid a forced four-app folder template.
- A UI surface may import its own modules and **public** workspace package exports. It must not import the private sources of another app, service client, or package using relative paths, `apps/` aliases or an internal `@bthwani/<owner>/clients|backend|database|contracts|src` path. Service API behavior must come from current owner contract exports, not code written inside the app.
- App package names (`@bthwani/customer`, `@bthwani/merchant`, `@bthwani/captain`, `@bthwani/control-panel`) are **not** shared-package contracts: one app may not import another app by its bare package name or subpath. Move truly shared functionality to a justified non-app owner package with a reviewed public export; do not bypass the import guard with computed imports.
- The blanket `src/features` prohibition is superseded by progressive implementation authorization. A scoped presentation feature may be added inside its existing app without a new admission vote; actual code must obey the canonical service contract, app ownership, private-export, single-route-root and authorization boundaries. No blind donor directory copy or placeholder-only feature qualifies as closure.
- Deterministic source import checks live under `tools/mobile/verify-application-boundaries.mjs`. The pinned TypeScript 7 lexical scanner checks static, re-export, literal dynamic and resolver imports, rejects nonliteral computed module calls, forbids cross-owner private paths and cross-renderer dependencies, and rejects new Stage-4 workspace owners or `src/app` route roots. Negative fixtures verify feature-file ownership independently of whether `src/features` directories currently exist. This remains a lexical guard, **not** full alias/computed-import dataflow tracing, cycle analysis, package-level builds, runtime authorization or route/contract E2E proof. `verify-app-foundations.mjs` preserves the pinned app-identity and renderer checks without rejecting feature folders merely for existing; `verify-application-boundaries.mjs` scans actual `app/` and `src/` feature imports for owner violations.

### Lean modular feature placement (approved progressive organization, 2026-11-16)

- **One principle, not four identical templates:** organize substantive presentation code by capability inside each existing app; create src/features/<capability>/ only when a real feature has consumers. Do not pre-create features, components, providers, shared, shell, bootstrap, tests or artificial Clean Architecture layers while unused.
- **Routes remain routes:** Expo Router and Next App Router continue to own their existing top-level app/ paths, layouts, navigation and metadata. A small route-local screen may remain colocated there; when its presentation or client-side state becomes substantial, its route delegates to a feature-owned screen. Refactoring must preserve paths, deep links, route parameters, metadata, accessibility and failure behavior.
- **Feature locality:** a feature keeps its screens, view components, presentation state, hooks and focused tests together, splitting into subdirectories only when doing so reduces actual complexity. It calls the public contract-derived client of Identity, DSH or WLT as needed; it does not own business policy, financial truth, authentication authority or persistent writes.
- **Reuse without dumping grounds:** prefer a feature-local component until a second genuine consumer justifies a reusable app-local module; use descriptive domain names where possible. An app-local src/components/ or src/providers/ directory is optional and justified by real consumers; do not introduce a generic shared/ dumping ground without a separately reviewed, tested placement rule. Cross-feature imports are reviewed for actual coupling; promote a reusable primitive instead of introducing circular feature dependencies. Cross-app reuse requires a justified exported workspace package, never private app imports.
- **Operator-specific Next.js boundaries:** apps/control-panel/app/(workspace)/ owns Operator route composition. Its src/features/ owns substantial Operator presentation and src/server/ contains server-only authenticated transport/adapters when required. app/api/ route handlers are added only for concrete authentication, security, same-origin, server-only integration or justified aggregation needs, never automatically for each owner API operation. Handlers do not become another Identity/DSH/WLT rules or data engine.
- **Tests and migration:** keep focused tests alongside their feature or in the app's established test location; tests/ at repository root is reserved for cross-owner integration. Before any move, trace every consumer and dynamic route, update imports/tests, and verify route identity, TypeScript, app boundary guards, and relevant runtime states. Do not measure quality by folder/file count or impose arbitrary line-count thresholds.

### Deep source directory grammar and executable enforcement (2026-11-16)

The following is **placement law**, not a requirement to create empty folders or a second capability registry. Extend an existing real feature when it fits; create only its needed subdirectories, and retain current working routes and Go package names until consumers have been migrated and tested. Checks operate on real directories (including new, not-yet-Git-tracked directories), not just the top-level tree.

| Area | Legal ownership and naming | Rejected drift |
| --- | --- | --- |
| Expo/Operator routes | One `apps/<surface>/app/` root; use framework-owned `_layout.tsx`, `[id].tsx` or Next `page.tsx`/route groups where applicable | A competing `src/app/`, or newly authored `partners`/`partner-onboarding` UI directories |
| Presentation features | One `apps/<surface>/src/features/<feature-name>/` per app, with lowercase-kebab-case capability names such as `stores`, `orders`, `cash-custody`; simple features may keep source files directly inside their named feature | Unowned source directly inside `src/` or `src/features/`, `src/feature/`, `features/features/`, CamelCase or generic capability names, copied donor `partners` |
| Feature subdivisions | Optional first tier: `screens/`, `components/`, `hooks/`, `queries/`, `mappers/`, `state/`, `tests/`; further meaningful nested directories use lowercase-kebab-case; feature source filenames use lowercase-kebab-case with standard platform/test suffixes | Unlimited unlabeled directories such as `misc/`, `legacy/`, or another feature root below a feature; files named `OrderCard.tsx` rather than `order-card.tsx` |
| App-local reuse | Optional `src/components/` or `src/providers/` with actual consumers; a second app needs a properly exported package instead | Generic app-wide state or duplicated design tokens, or creating those folders empty by quota |
| Operator server adapters | Only `apps/control-panel/src/server/` where server-only transport is needed, in `auth/`, `clients/`, or `transport/` | A duplicate business writer, shadow `app/api/` for every owner endpoint, or server-only implementation in Expo |
| Go owner backend | `services/{identity,dsh,wlt}/backend/cmd/<owner>/*.go` and `backend/internal/<domain>/**/*.go`; package directories are lowercase Go identifiers, not framework-layer quotas | Go sources directly in `backend/` or under arbitrary `backend/usecases/`, `internal/misc/`, or new `internal/partners/` |
| SQL | `services/<owner>/database/migrations/NNN_descriptive_name.sql` using the actual owner's applied sequence; keep applied history immutable | SQL inside `backend/`, outside `migrations/`, or an unnamed `001.sql` |
| OpenAPI and clients | One owner root `contracts/openapi/<owner>.openapi.yaml`, its `paths/<domain>.yaml` fragments, and public contract-derived `clients/index.ts` | `contracts/openapi/path/`, owner-crossing private imports, unreferenced fragments, a second maintained DTO catalog |

**Naming compatibility:** the new presentation name is **Merchant** (`merchant`, `merchants`, `merchant-onboarding`), not Partner. Historical `partner` spellings in archived paths, already-issued permission identifiers, capability IDs and finance contracts remain unchanged until an explicitly tested compatibility migration. A Merchant actor belongs to Identity; Store ownership and scoped access belong to DSH; agreements and monetary postings belong to WLT.

**Go internal is deliberate:** Go's native `internal/` import boundary is preserved; the old DSH list of packages is *not* the new target. Current `session/`, `discovery/`, and `storeavailability/` remain legal. A deeper `stores/availability/` package would require a justified, tested move rather than a second implementation. No generic domain/application/infrastructure ladder, package count, or service `hr` is mandated. WLT keeps two tracked placement guides; `backend/Dockerfile` and `backend/project.json` become legal only alongside a real `go.mod` and `cmd/wlt/main.go`, with owner-backed acceptance still required.

**How the rule is enforced:** `tools/mobile/verify-application-boundaries.mjs` scans authored presentation paths recursively and checks private imports; `tools/governance/verify-foundation.mjs` admits Go/SQL/OpenAPI files only in owner locations. Both have negative fixtures run in the existing `check:apps` and `check:foundation` CI paths. These are structural checks, not proof of endpoint semantics, runtime payments, legal compliance or 100% error-free future development. A genuinely new presentation layer or Go domain must update the owning placement rule and its tests together rather than evade the guard.

### Names which must not be conflated

- **Actor/Merchant** is an Identity-authenticated person or delegated role; **Store** is a DSH-owned business resource. A Merchant may operate multiple Stores. See `governance/identity.md` and `governance/stores.md` for Product semantics.
- **MARKETPLACE/DIRECT** is a Store relation; **COMMISSION/SUBSCRIPTION** is a WLT agreement model; **PLATFORM_MANAGED/STORE_MANAGED** is collection responsibility. These are independent dimensions, not parallel Store or Order implementations. Historical `BTHWANI_PARTNER/INDEPENDENT_STORE` values require an approved compatibility decision before mutation.
- **Clients package** means public, contract-derived callers. An exported empty `clients/index.ts` only prepares the TypeScript workspace; it is neither a usable SDK nor a running Go **backend**. OpenAPI `paths: {}` fragments are reserved labels, not active operations.
- **Fresh Baseline** installs a new isolated empty database; **migration** is an immutable applied upgrade history. They must not be conflated, renumbered or applied interchangeably. See `governance/safety.md`.
- **Foundation PASS**, **required GitHub check PASS**, **governance READY**, **native runtime PASS** and **production release approved** are independent gates. Main is the protected branch, `archive/legacy-pre-refoundation-20261114` is read-only donor history, and the Worktree is a directory; no branch change implicitly migrates databases or authorizes deployment.

## Structural closure
A slice is structurally accepted only when the winning path, every affected consumer, generated API, SQL/config reference and test is updated, the losing path is gone, and source/runtime proof is tied to the exact accepted revision. Otherwise report NOT_RUN, BLOCKED or REVIEW_BLOCKED; do not infer correctness from Git status alone.
