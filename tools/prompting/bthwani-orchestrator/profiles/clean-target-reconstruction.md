## Purpose

Use this profile only when the invocation supplies a separate legacy/donor repository/ref and BThwani is reconstructed directly into a clean target repository.

It specializes the canonical Orchestrator for the two-repository model. It does not define Product meaning, target Product breadth, repository current state or closure independently.

~~~text
DONOR = READ_ONLY_FORENSIC_SOURCE_CORPUS
TARGET = ONLY_MUTABLE_CANONICAL_CANDIDATE
DONOR_SHAPE != TARGET_TOPOLOGY
DONOR_EXISTENCE != SURVIVAL_RIGHT
DONOR_REQUIRED_VALUE != DONOR_CONTAINER_SURVIVAL
~~~

## Direct-to-canonical construction law

Build required target value directly in the canonical owner location. Never recreate a proven losing donor container merely to reproduce a same-repository migration sequence.

~~~text
DONOR_PATH != TARGET_PATH_AUTHORITY
DONOR_REQUIRED_VALUE → EXTRACT
TARGET_CANONICAL_OWNER → BUILD/REIMPLEMENT/REGENERATE
LOSING_DONOR_CONTAINER → REJECT_FROM_TARGET_AFTER_VALUE_EXTRACTION
LOSING_TARGET_CONTAINER → FOLLOW_03_MIGRATION/CUTOVER/DELETION_OWNER
~~~

Historical/generic donor shapes are translated only after semantic ownership proof. Examples of losing shape classes include generic `core`, `shared`, app-shaped service frontend trees, generic provider/people/data-runtime/resilience buckets and pass-through app runtime parents. The exact destination is derived from current durable ownership; this profile never grants automatic survival to a named destination.

## Semantic versus deployable-service admission

A durable semantic responsibility does not automatically imply an independent deployable service.

~~~text
SEMANTIC_RESPONSIBILITY_ADMITTED
!=
INDEPENDENT_DEPLOYABLE_SERVICE_ADMITTED
~~~

This is particularly important for control-plane, notification/search, future HR/people and generic integration responsibilities. Service admission remains governed by current architecture evidence.

## Cross-repository replacement semantics

When wording from same-repository refactoring refers to a losing source path, translate it as:

~~~text
DONOR LOSING SOURCE
→ INSPECT/EXTRACT REQUIRED VALUE
→ PROVE TARGET OWNER
→ REIMPLEMENT/REHOME DIRECTLY IN TARGET
→ VERIFY PARITY OR DELIBERATE GOVERNED IMPROVEMENT
→ DO NOT IMPORT LOSING DONOR CONTAINER

SAME LOSING SHAPE ALREADY EXISTS IN TARGET
→ BUILD/PROVE WINNER
→ MIGRATE TARGET DATA/CONTRACTS/CONSUMERS
→ CUT OVER WRITERS/READERS/ROUTES/EXPORTS/CONFIG/RUNTIME
→ DISABLE OLD WRITES
→ DELETE LOSER/ALIASES/COMPATIBILITY
→ VERIFY NEGATIVE SPACE
~~~

Never mutate the donor to make target closure easier.

## Durable-data reconstruction

When required donor data truth must be reconstructed:

~~~text
PROVE_REQUIRED_DURABLE_TRUTH
→ PROVE TARGET DATA OWNER/SHAPE
→ DEFINE DETERMINISTIC TRANSFORM
→ MIGRATE/BACKFILL OR RESEED ONLY AS GOVERNED
→ VERIFY COUNTS/KEYS/CONSTRAINTS/INVARIANTS
→ CUT OVER TARGET WRITER/READERS
→ RECONCILE
→ PROVE CANONICAL READBACK
→ DELETE TARGET LOSING STORAGE IF ANY
~~~

Donor schema is evidence, not target schema authority.

## Contract/runtime/deployable identity preservation

Repository reconstruction must explicitly account for required external identities and bindings that can be expensive or unsafe to recreate, including materially applicable:

~~~text
MOBILE PACKAGE/BUNDLE IDENTIFIERS
EXPO/EAS PROJECT/UPDATE/SIGNING IDENTITY
URI SCHEMES/DEEP-LINK IDENTITY
WEB HOSTING/BUILD ROOT/BASE PATH
PROVIDER PROJECT/WEBHOOK/CALLBACK IDENTITY
DATABASE/QUEUE/BUCKET EXTERNAL BINDINGS
OBSERVABILITY PROJECT/RELEASE IDENTITY
PUBLIC API/CONTRACT COMPATIBILITY WITH REAL EXTERNAL CONSUMERS
~~~

Preserve or intentionally migrate the required identity; never preserve a losing repository container merely because the identity was configured there.
