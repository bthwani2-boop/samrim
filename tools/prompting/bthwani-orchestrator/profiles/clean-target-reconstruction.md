## 1. Model

~~~text
DONOR = READ-ONLY FORENSIC EVIDENCE
TARGET = ONLY MUTABLE CANONICAL CANDIDATE
DONOR SHAPE != TARGET TOPOLOGY
DONOR EXISTENCE != SURVIVAL RIGHT
REQUIRED DONOR VALUE != DONOR CONTAINER SURVIVAL
~~~

Target meaning/ownership comes from current Governance and explicit human decisions. Current target implementation truth comes from the target source/runtime.

## 2. Direct-to-canonical reconstruction

For every material donor atom relevant to the authorized scope:

~~~text
IDENTIFY ATOM
→ PROVE WHETHER IT IS STILL REQUIRED
→ PROVE CURRENT TARGET OWNER
→ PRESERVE / REFINE / MERGE / REHOME / REIMPLEMENT / REGENERATE / REJECT
→ BUILD DIRECTLY IN CANONICAL TARGET
→ VERIFY
~~~

Do not recreate a known losing donor container merely to repeat the donor's migration path.

~~~text
DONOR_PATH != TARGET_PATH_AUTHORITY
COPIED_BECAUSE_DONOR_HAD_IT = FORBIDDEN
UNKNOWN_AND_SKIPPED = FORBIDDEN
SILENT_REQUIRED_TRUTH_LOSS = FORBIDDEN
~~~

## 3. Donor evidence universe

Inspect only donor classes capable of changing the authorized result:

- current donor code/tree;
- material Git history/diffs/deletions;
- old Product/Governance/Docs when they can reveal still-required meaning;
- schema/migrations/data;
- contracts/generation/runtime/configuration;
- tests/fixtures/mocks;
- CI/guards/tools;
- external/deployable identities and assets when material.

For `ACTIVE_SLICE`, exhaust only the complete donor cone that can change that slice. Do not expand Product breadth merely to exhaust unrelated history.

For explicit `FULL_TARGET`, repository-wide donor disposition may be required.

## 4. Required-truth accounting

Before destructive target construction, account for all materially applicable:

~~~text
CAPABILITY / JOURNEY / ACTOR / SCOPE
CANONICAL OWNER / WRITER / READBACK
DURABLE DATA / MIGRATION / RECONCILIATION
CONTRACT / EVENT / GENERATED BINDING
RUNTIME / CONFIG / PROVIDER
SECURITY / PRIVACY / FINANCE
SURFACES / FAILURE / RECOVERY
TEST / ASSURANCE
DEPLOYABLE / EXTERNAL IDENTITY
~~~

The accounting is ephemeral execution evidence. Do not create another permanent census/ledger file.

## 5. Service/container admission

A donor service/folder/module name does not prove a target service/container.

~~~text
SEMANTIC RESPONSIBILITY ADMITTED
!=
INDEPENDENT DEPLOYABLE SERVICE ADMITTED
~~~

This applies especially to control-plane, people/HR, notification/search, generic integration and infrastructure-style donor boundaries.

## 6. Durable data reconstruction

When donor data truth must survive:

~~~text
PROVE REQUIRED TRUTH
→ PROVE TARGET DATA OWNER/SHAPE
→ DEFINE DETERMINISTIC TRANSFORM
→ MIGRATE/BACKFILL/RESEED ONLY AS GOVERNED
→ VERIFY COUNTS/KEYS/CONSTRAINTS/INVARIANTS
→ CUT OVER TARGET WRITER/READERS
→ RECONCILE
→ PROVE CANONICAL READBACK
→ DELETE TARGET LOSER
~~~

Donor schema is evidence, not target schema authority.

## 7. External/deployable identity

Preserve or intentionally migrate materially required:

- mobile package/bundle identifiers;
- Expo/EAS project/update/signing identity;
- URI/deep-link identity;
- web hosting/build-root/base-path identity;
- provider project/webhook/callback identity;
- database/queue/bucket external bindings;
- observability project/release identity;
- public contract compatibility with proven external consumers.

Do not preserve a losing repository container merely because the identity was configured there.

## 8. Closure boundary

For `ACTIVE_SLICE`, closure requires zero unaccounted donor truth capable of changing the authorized slice.

For `FULL_TARGET`, closure may require repository-wide material donor disposition.

This profile never declares Product/repository completion. `../04-VERIFY-REDIAGNOSE-CLOSE.md` and its routed verification owners do.
